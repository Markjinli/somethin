结论

一个自包含,一个薄编排

两家都叫"Clash 客户端",但"基础设施"这个词落在它们身上指的是完全不同的东西。FlClash 把整条链路都收进自己仓库:核心是自己 fork 的、控制协议是自己造的、提权服务是自己写的。Clash Verge Rev 反过来,把自己压成一层薄编排——核心用上游原版二进制,控制走核心自带的 API,连提权服务都在另一个仓库里。

FlClash

自包含:全部源码在仓库里核心 fork + 自研 IPC 协议 + 仓库内 Rust 提权服务。版本完全确定,组件边界少。代价是要自己维护一整套协议,而且核心跟不上上游。

Clash Verge Rev

薄编排:关键件在仓库外上游 stock 核心 + 核心自带 REST API + 外部服务仓库(预编译二进制)。核心永远最新,服务能独立升级。代价是多出一整套版本协商复杂度。

控制面拓扑

整个对比里最反直觉的一点

FlClash 完全不用 mihomo 的 REST API——external-controller 默认关闭,代码里根本没用它。它自己造了一套协议,还把服务端放在 App 侧:App 创建监听,核心作为客户端连进来。下图两行的方框位置完全对齐,只有箭头方向不同,差异一眼可见。

四个分歧点

真正决定"基础设施架构"长什么样的地方

01

核心是自有的,还是上游的

FlClash

维护一个 mihomo 私有 fork,子模块钉死 SHA 70f0570…,靠 go.mod 的 replace 引入。版本完全确定、可复现,但跟不上上游——上游的修复要自己 rebase。

Verge

每次构建拉上游最新 mihomo。永远跟得上,但同一个 commit 在不同时间构建会得到不同的核心,核心行为可能随上游悄悄漂移。

02

控制面谁说了算

FlClash

自造协议、自己实现服务端。可控性最高,连 Windows 上还要额外校验命名管道对端 PID 是不是 helper 报告的那个。

代价:这套协议得自己长期维护,而且核心的既有能力(API)被绕过了。

Verge

直接用核心自带 REST API,只把传输从 TCP 换成管道/socket(默认 TCP 端口是关的)。省事,但要处理 API 兼容。

配套细节:管道 SDDL 收紧到仅属主 + SYSTEM + Administrators。

03

提权产物在不在仓库里

FlClash

helper 服务是仓库内的 Rust 源码(services/helper/),读写改都在一起。Windows 下装成 AutoStart 的 LocalSystem 服务,启动核心前会比对编译期嵌入的 CORE_SHA256。

Verge

服务在另一个仓库,以预编译二进制下载。于是必须有协议版本协商——MIN_REQUIRED_SERVICE_REVISION、NeedsReinstall、能力探测、不匹配就降级回 sidecar。

换来的是服务能独立于 GUI 升级。

04

macOS 两条完全不同的路

FlClash

没有 helper。用 osascript 提权执行 chown root:admin && chmod +sx,把核心设成 setuid root。因为核心成了 root,还得反向给用户主目录补一条继承 ACL,让它还能写进去。

Verge

正规的 launchd LaunchDaemon,装到 /Library/LaunchDaemons/。安装时走 osascript … with administrator privileges。

两家都没有用 NetworkExtension。

两边都没写的

"VPN 基础设施"里最难的那几块,两家客户端都没实现

这可能是整份对比里最该记住的一条。上面那些差异都在编排层,而真正干活的数据面,两家都交给了 mihomo。

  • TUN 网卡 两家仓库里 wintun 都是零命中——没有驱动、没有 DLL、没有安装步骤(Verge 只在历史 changelog 里留下两处旧版本的字样)。网卡由 mihomo 内嵌的 wintun 自己释放,客户端只负责往配置里写那个 tun: 块。
  • 路由表 两边都没有一行 netsh / route add / netlink 代码。全靠 auto-route: true 丢给核心。服务端 IP 的绕过路由也是核心装的。
  • DNS 解析 fake-ip、dns-hijack: any:53、fallback 过滤,全是写进 YAML 的 mihomo 配置。客户端没有解析器、没有 DNS 缓存。
  • 代理协议 出站、嗅探、规则引擎——客户端一行都没实现,全是核心的。
  • 唯一的 OS 级 DNS 操作 两边都只在 macOS 上动系统 DNS,而且都往里面钉一个国内公共解析:FlClash 钉 223.5.5.5,Verge 钉 114.114.114.114。但触发条件不同——Verge 那边限定在 fake-ip 分支里,配置显式写 redir-host 就不会钉。所以这是个行为差异,不是相同做法。

共同的失败模式

两家都会静默丢掉 TUN。FlClash 的 helper 起不来或核心校验失败时,退回非提权核心,TUN 就没了——不报错。Verge 在非管理员且没装服务时,强制关掉 TUN 并把偏好持久化改掉,再给个提示。

这就是"看起来连上了、实际没走全局"这类体验的来源。两家的判定逻辑也都是显式的:Verge 是 RunState::tun_capable() = is_admin || service_usable()。

读取范围

这份对比没看到什么

FlClash 的 mihomo fork 没读到

core/Clash.Meta 是 git 子模块,浅克隆是空目录。凡涉及核心内部(Windows TUN 网卡具体怎么建、路由怎么装)的结论,都是"客户端侧没有这段代码"的推断,不是直接读到的实现。子模块拉下来就能补上。

Verge 的服务端根本不在这个仓库

提权服务在外部仓库 clash-verge-service-ipc,以预编译二进制形式引入。所以它的 IPC 线格式细节、它内部怎么做提权操作,都没有源码可读——只能从客户端侧的调用与能力协商反推。

两边的核心本身都没读源码

FlClash 是子模块没拉;Verge 用的是上游 stock 二进制。涉及 mihomo 内部行为(fake-ip 具体实现、wintun 释放时机、路由安装顺序)的部分,两份报告都只能标注为"由核心负责",没有验证。
